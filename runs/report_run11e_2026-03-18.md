## 1. Design Summary

Run 11e tests three interventions designed to address findings from Runs 11b–11d:

- **Change J:** v4 Context Graph with redesigned OBJECT_RELEVANCE_SCREENING (subset testing, per-object scorecard, order variation, small-subset enforcement) — addresses the 100% ORS backstop fire rate in 11c by making ORS guidelines more actionable
- **Change K:** Lean Dynamic Behaviors (3 of 5 behaviors active: `order_hypothesis`, `stochasticity_hypothesis`, `exploration_stagnation` without state injection) — addresses 11c's DB interference pattern by removing `moderator_detection` and `dimension_discovery` state injection
- **Desync fix:** Correction message injected when CG engine rejects an agent's transition request — addresses state disagreements observed in 11c/11d trace analysis

All changes are applied to CG-only (Cell B) and full CG+DB (Cell C). Cell A (base_llm) is unchanged.

**Key changes from Run 11c:**
- v4 CG: Redesigned ORS guidelines with explicit subset-testing protocol (test 2-3 object subsets, maintain scorecard, note order variations)
- `object_screening_max_steps=20` (lowered from 25 in 11c, matching 11d)
- Lean DB: Only 3 behaviors (removed `rule_change_hypothesis`; `exploration_stagnation` sends notification only, no DIMENSION_DISCOVERY injection)
- Desync fix in `cg_agent.py`: Pending correction message on failed transitions
- Seeds 1501–1515 (vs 1301–1315 in 11c)
- Budget cap $150 (same as 11c)

## 6. DB Analysis (Cell C)

### 6.1 Behavior Fire Rates

| Behavior | Fire Rate | Mean Fire Step | Mean Score | Comparison to 11c |
|----------|:---------:|:--------------:|:----------:|:------------------:|
| exploration_stagnation | 15/15 (100%) | 8.7 | 6.5 | 15/15 (100%) — same |
| order_hypothesis | **15/15 (100%)** | 42.7 | 7.5 | 14/15 (93%) — slight increase |
| stochasticity_hypothesis | **3/15 (20%)** | 80.3 | 9.0 | 9/15 (60%) — **−40pp** |

**Critical regression: stochasticity_hypothesis fire rate dropped from 60% (11c) to 20% (11e).** Despite identical threshold (6.0), the lean DB config produces far fewer stochasticity detections. Possible explanations:
1. The removed `dimension_discovery` injection in 11c created contextual cues that helped the trigger model recognize stochasticity
2. With fewer DB notifications competing for attention, the stochasticity signal is more easily overwhelmed by the order signal
3. `order_hypothesis` fires 100% of the time (vs 93% in 11c) and dominates the agent's attention, leaving less exploration budget for stochasticity detection

### 6.2 Competitive Inhibition

`stochasticity_hypothesis` was suppressed in **12/15 episodes (80%)**. In suppressed episodes, the trigger model scored stochasticity evidence at 0–3, well below the 6.0 threshold. The `order_hypothesis` consistently out-competes `stochasticity_hypothesis` because:
- `order_hypothesis` fires earlier (mean step 42.7 vs 80.3)
- Once ORDER_TESTING is injected, the agent's exploration shifts to permutation testing, generating observations that are legible as "order matters" to the trigger model but not as "results are probabilistic"

### 6.3 exploration_stagnation (Notification-Only)

The lean `exploration_stagnation` behavior fires at step 8.7 on average (range 7–12), providing a notification without state injection. Fire rate is 100%, identical to 11c. The notification-only design (no DIMENSION_DISCOVERY injection) appears to have no measurable effect on agent behavior — agents proceed through the same IE→ORS transition regardless.

| 11b | 1201–1215 | 27% |
| 11c | 1301–1315 | 13% |
| 11e | 1501–1515 | 0% |

This monotonic decline suggests the seed range 1501–1515 generates particularly challenging rules. Cross-cell verification confirms: no cell exceeds 7% on these seeds. Future analysis should control for seed difficulty by running multiple CG versions on the same seed set.

### 12.2 Why Did cg_only (v4) Fail?

Cell B dropped from 20% (v2 CG, 11c) to 0% (v4 CG, 11e). Three factors:
1. **Harder seeds** (Cell A also collapsed)
2. **Shorter ORS window** (20 vs 25 steps) reduces time for initial object screening
3. **v4 ORS guidelines may over-specify behavior** — by prescribing a specific subset-testing protocol, the guidelines may constrain agents from more effective free-form exploration

The 14/15 canonical trajectory pattern in Cell B (identical to 11c) shows that v4's guideline changes don't alter the *structure* of exploration — they only affect *what happens within ORS*. If ORS content doesn't change outcomes, the ORS redesign was architecturally neutral and the performance difference is seed-driven.

### 12.3 The Lean DB Paradox

The lean DB config achieved its intended goal (C > B for the first time) but through an unexpected mechanism: **not by improving Cell C, but by Cell B's collapse on hard seeds.** Cell C at 6.7% is identical to 11c. The lean DB's removal of `dimension_discovery` and `moderator_detection` had no positive effect on Cell C performance.

Worse, stochasticity detection regressed from 60% to 20%. The lean DB config inadvertently removed contextual cues that helped the trigger model recognize stochastic patterns. The `dimension_discovery` state injection — previously considered harmful — may have created cognitive scaffolding that improved downstream stochasticity recognition.

### 12.4 DB as Order-Detection Engine

The most reliable DB contribution in 11e is **order awareness**. Cell C agents guessed an order-related rule type in 87% of episodes (vs 40% for Cell B). The `order_hypothesis` behavior fires 100% of the time and drives ORDER_TESTING visitation to 87%. The lean DB config successfully concentrates DB's value into order detection, but this one-dimensional contribution isn't sufficient to compensate for the object identification bottleneck.

### 12.5 Architectural Implications

Run 11e reinforces the core finding from 11c: **object identification is the binding constraint on ORDER_STOCHASTIC**. Neither CG redesign (v2→v4) nor DB configuration changes (5-behavior→3-behavior) address this bottleneck. The v4 ORS guidelines explicitly instruct subset testing and scorecard maintenance, yet agents still submit all 5 objects in 9/13 Cell C answers. The issue is not *what the guidelines say* but *whether the agent can extract diagnostic signal from stochastic observations*.

With p=0.7 activation probability, individual object tests give inherently noisy results. A correct 3-object subset activates ~70% of the time. A 4-object set containing the correct 3 also activates ~70% of the time (the extra object is irrelevant). The agent cannot distinguish "3 correct + 1 distractor" from "3 correct" through activation rates alone — both patterns produce identical statistical signatures. Distractor elimination requires systematic elimination testing (try without object X — does activation rate change?), which no CG version has explicitly guided.
