## 5. DB Fire Rates and Competitive Inhibition Analysis (Cell B)

This section addresses the planning prompt's primary architectural question (Sections 4.3–4.4): how do the dynamic behaviors interact in a multi-dimensional condition where two DBs (`order_hypothesis` and `stochasticity_hypothesis`) are simultaneously relevant?

### 5.1 Per-Behavior Fire Rates

| Behavior | Fire Rate | Mean Step of First Fire | Role |
|----------|:---------:|:-----------------------:|------|
| exploration_stagnation | 7/15 (47%) | 8.1 | Fires early when agent plateaus |
| order_hypothesis | 15/15 (100%) | 11.0 | Detects order-sensitive evidence |
| stochasticity_hypothesis | 15/15 (100%) | 22.1 | Detects probabilistic activation |
| rule_change_hypothesis | 14/15 (93%) | 22.1 | False positive — no rule change occurred |

Both target behaviors (`order_hypothesis` and `stochasticity_hypothesis`) fired in every episode. The consistent firing sequence is: stagnation (step ~8, when present) → order (step ~11) → stochasticity and rule_change (step ~22). The ~11-step gap between order and stochasticity detection reflects the logical dependency: the agent must first identify the relevant objects and ordering before it can accumulate enough repeated tests to detect probabilistic activation.

`rule_change_hypothesis` fired in 14/15 episodes despite no rule change occurring. This is a known false positive: when the agent observes inconsistent results from the stochastic activation, the rule_change DB interprets this as evidence of a changed rule. The false positive is architecturally benign in this condition — it directs the agent to a MODERATOR_DETECTION state that doesn't interfere with the correct exploration path.

### 5.4 Competitive Inhibition: Co-Threshold and Suppression

The planning prompt identified competitive inhibition as a primary diagnostic: when two DBs are simultaneously relevant, does winner-take-most suppress a needed signal?

**Aggregate competitive inhibition metrics:**

| Metric | Value |
|--------|-------|
| Total evaluation steps (all episodes) | 306 |
| Steps where 2+ behaviors scored ≥ 7.0 | 6 (2.0%) |
| Steps where a behavior was suppressed (≥ 7.0, didn't fire) | 1 (0.3%) |
| Suppression rate (suppressed / co-threshold) | 1/6 = 16.7% |

**Suppression detail (single event):**

| Ep | Step | Suppressed Behavior (score) | Winning Behavior (score) | Outcome |
|:--:|:----:|:---------------------------:|:------------------------:|:-------:|
| 5 | 31 | rule_change_hypothesis (7.0) | stochasticity_hypothesis (9.0) | PASS |

The suppressed behavior (`rule_change_hypothesis`) fired on the very next step (32), so the suppression delayed the signal by a single step with no impact on the episode outcome.

### 5.5 Competitive Inhibition Interpretation

**The competitive inhibition mechanism is essentially a non-factor in this condition.** Only 6 of 306 evaluation steps (2.0%) produced co-threshold events, and only 1 of those 6 resulted in actual suppression. The reason is architectural: behaviors reach threshold at different times rather than competing simultaneously. The typical sequence — order fires at step ~11, stochasticity fires at step ~22 — means the two target behaviors are rarely in direct competition.

This answers the planning prompt's Question 3 decisively. The pre-specified follow-up (margin-based co-firing) is **not motivated** by this data. The winner-take-most mechanism does not suppress needed signals in the ORDER_STOCHASTIC condition because the temporal separation between behavior firing is large enough that competition rarely arises.

However, this finding is specific to the 2-object condition where the order search resolves early. In a 3-object ORDER_STOCHASTIC condition, `order_hypothesis` might fire later (more steps needed to resolve 3-object ordering), potentially overlapping with `stochasticity_hypothesis`. The co-firing question remains open for higher-dimensional conditions.

### 6.3 RELIABILITY_TESTING: Never Reached

The most notable finding is that **RELIABILITY_TESTING was never entered in any episode**, despite `stochasticity_hypothesis` firing in all 15 episodes. The CG state machine transitions to RELIABILITY_TESTING when the agent explicitly shifts to measuring activation probability — but in practice, the agent either (a) detected stochasticity implicitly through accumulated observations without entering the formal testing state, or (b) the CG transition conditions for RELIABILITY_TESTING require evidence beyond what the `stochasticity_hypothesis` notification alone provides.

This has implications for future combined conditions: the RELIABILITY_TESTING state may need a lower transition threshold or a direct trigger from the `stochasticity_hypothesis` DB fire to ensure agents enter a systematic probability-estimation phase.

### 6.4 CG Traversal vs Accuracy: A Paradoxical Result

| CG Pattern | Episodes | Accuracy | Avg Steps |
|------------|:--------:|:--------:|:---------:|
| INITIAL_EXPLORATION only | 8 | **7/8 (87.5%)** | 60.0 |
| Multi-state traversal | 7 | **3/7 (42.9%)** | 63.3 |

Episodes that never left INITIAL_EXPLORATION succeeded at 87.5%, while episodes that traversed multiple CG states (entering ORDER_TESTING) succeeded at only 42.9%. This is a paradoxical result: **more CG guidance correlates with worse outcomes**.

The likely explanation is confounding, not causation. DB behaviors fire when the agent encounters ambiguous evidence — which happens more on episodes where the stochastic RNG produces confusing outcomes (e.g., A→B fails on early trials due to p=0.7 bad luck). The CG transitions are triggered by difficulty signals, so "more CG states" is a proxy for "harder episode" rather than "CG is hurting." The 8 episodes that stayed in INITIAL_EXPLORATION were likely easy realizations where the agent quickly found A→B, observed activation, and submitted without encountering enough contradictory evidence to trigger DB firing.

However, the data does rule out the hypothesis that CG traversal provides a systematic rescue effect. Even in episodes where the scaffold fully engaged (ORDER_TESTING → VERIFICATION), the agent failed 4 out of 7 times.

## 7. Comparison with Prior Runs

### 7.1 Cross-Run Context

| Run | Condition | Objects | Rule Complexity | Max Steps | base_llm | full_cg_db |
|-----|-----------|:-------:|----------------|:---------:|:--------:|:----------:|
| 10e (pooled) | ORDER_SENSITIVE | 3-obj rule, 5-obj space | 3-obj order | 75 | ~55% | ~20% |
| 10f Cell A/B | ORDER_SENSITIVE | 4-obj rule, 6-obj space | 4-obj order | 100 | 20% | 40% |
| **11a** | **ORDER_STOCHASTIC** | **2-obj rule, 5-obj space** | **2-obj order + p=0.7** | **75** | **73%** | **67%** |

### 7.2 Interpretation

Run 11a's high accuracy (73%/67%) vs Run 10e/10f's lower accuracy (20-55%) is primarily driven by **rule complexity**, not condition type:

- **2-object rule → only 1 ordering to discover** (A→B vs B→A). With 5 objects, the agent needs to narrow from C(5,2)=10 candidate pairs × 2 orderings = 20 candidates. The order search space is 20.
- **3-object rule → 6 orderings per triple.** With 5 objects, C(5,3)=10 triples × 6 orderings = 60 candidates.
- **4-object rule → 24 orderings per quad.** With 6 objects, C(6,4)=15 quads × 24 orderings = 360 candidates.

The combinatorial explosion (20 → 60 → 360) dominates difficulty. Adding stochasticity to a 2-object rule is significantly easier than deterministic 3- or 4-object ordering.

**The combined condition (order + stochastic) does add difficulty**, but it's a ~15-25pp penalty on top of a very high 2-object baseline, not a multiplicative difficulty increase. The stochasticity penalty manifests as:
- 4 rule_type confusion errors (agents who got objects and order correct but missed stochasticity)
- Slightly higher step counts (avg 57.9/61.6 vs ~40-50 typical for pure 2-obj conjunctive)

### 7.3 Scaffold Advantage Comparison

| Run | Condition | full_cg_db − base_llm |
|-----|-----------|:---------------------:|
| 10e (pooled) | ORDER_SENSITIVE, 3-obj | −35pp (base_llm higher) |
| 10f (100 steps) | ORDER_SENSITIVE, 4-obj | **+20pp** |
| 10f (125 steps) | ORDER_SENSITIVE, 4-obj | −10pp |
| **11a** | **ORDER_STOCHASTIC, 2-obj** | **−6.7pp** |

The scaffold advantage appears only when the task is moderately difficult (10f at 100 steps). When the task is easy (11a, 2-obj) or very hard (10e, 3-obj at 75 steps), there is no scaffold advantage. This is consistent with a **scaffolding sweet spot** hypothesis: the overhead of dynamic behaviors (extra exploration, trigger evaluations) only pays off when the base task is hard enough to benefit from structured exploration but not so hard that the extra steps are wasted.

## 9. Synthesis

### 9.1 Does ORDER_STOCHASTIC work as a condition?

**Yes.** The environment, text interface, scoring, and run infrastructure all functioned correctly. Both agents understood the prompt, explored systematically, and attempted to identify both order and stochasticity. The 86-87% stochasticity detection rate confirms agents CAN identify the combined condition — it's not opaque.

### 9.2 Is 2-object ORDER_STOCHASTIC too easy?

**Partially.** At 73%/67% accuracy, the condition is too easy to reliably measure a scaffold advantage — both agents are near ceiling for a 2-object search. The 2-object order search space (20 candidates) is small enough that both architectures can brute-force it within 75 steps. The stochastic component adds ~15-25pp difficulty beyond what a pure 2-object order-sensitive rule would produce, but it's not enough to create a floor-to-ceiling gradient where scaffolding matters.

### 9.3 Competitive Inhibition Verdict

**Not a bottleneck in this condition.** The pre-specified follow-up (margin-based co-firing) is not motivated. The two target behaviors (`order_hypothesis` and `stochasticity_hypothesis`) fire ~11 steps apart on average, creating natural temporal separation that avoids competitive inhibition. Only 1 suppression event occurred across 306 evaluation steps, and it involved the irrelevant `rule_change_hypothesis` — not the two target behaviors competing with each other. The winner-take-most mechanism is architecturally benign here.

**Open question for 3-object ORDER_STOCHASTIC:** With a more complex ordering task, `order_hypothesis` may fire later, potentially overlapping with `stochasticity_hypothesis`. The competitive inhibition question should be re-examined if the 3-object condition produces closer firing times.

### 9.4 CG State Machine Verdict

**Partially functional, with one gap.** The CG state machine navigated the combined condition coherently when engaged — episodes that entered ORDER_TESTING followed logical paths (COMBINATION_TESTING → ORDER_TESTING → VERIFICATION). However, RELIABILITY_TESTING was never reached in any episode, meaning the formal probability-estimation phase was never activated despite stochasticity being detected in 87% of episodes. The agent detected stochasticity implicitly through accumulated observations rather than through the structured RELIABILITY_TESTING protocol. This represents an under-utilization of the CG architecture — the state machine offers a testing mode that the agent never uses.

The paradoxical finding that CG traversal correlates with lower accuracy (42.9% vs 87.5%) is likely confounded by episode difficulty but rules out the hypothesis that CG navigation provides a systematic rescue effect in the combined condition.

### 9.5 Decision Tree Resolution

Applying the planning prompt's decision tree (Section 4.2):

```
Combined condition breaks ceiling?
└── NO, both near stochastic floor (73–80%)
    └── Both DBs fire but no accuracy benefit
        → Combined condition recapitulates stochastic null.
          The order dimension adds no additional challenge.
          Boundary condition finding.
```

Both agents are near the stochastic-only accuracy range (73-80% from Run 03). The combined condition does not produce separation beyond what stochastic-only already showed. The order dimension at 2 objects is too easy to create meaningful additional challenge.

### 9.6 Recommendations

**1. Scale to 3-object ORDER_STOCHASTIC.** The 3-object search space (60 candidates × stochastic verification) should produce accuracy in the 20-40% range where scaffold effects have been observed (cf. Run 10f at 100 steps). This also tests whether competitive inhibition becomes relevant when `order_hypothesis` fires later. Design:

**3. Don't invest further in 2-object ORDER_STOCHASTIC.** The n=15 pilot is sufficient to establish the condition works and the ceiling is too high for scaffold differentiation.

**4. Investigate RELIABILITY_TESTING activation.** The 0% entry rate for RELIABILITY_TESTING suggests the CG transition conditions need revision. ## Appendix A: Reporting Gap — Step-Level `db_notifications` Not Populated

### What Happened

The original version of this report (2026-03-15) omitted the competitive inhibition analysis (now Section 5) and CG state trajectories (now Section 6), both of which were flagged as non-optional in the planning prompt (Sections 4.3–4.4, 6.5). The DB score data and CG state data were fully logged but the report author did not extract them.

The root cause is a **misleading data layout** in the trace JSON files. The step-level trace array (`steps[]`) includes a `db_notifications` field that is **always an empty array** — the `StepTrace` dataclass in `episode_runner.py` defines this field with a default of `[]` but the episode runner never populates it from the agent's data. A report author scanning the step-level traces would see no DB activity at all and might conclude the data was not captured.

The actual DB data lives in a separate location within the same JSON file:

| Data | Location in Trace JSON | Populated? |
|------|------------------------|:----------:|
| DB score vectors (all behaviors, every step) | `agent_trace.db_score_log` | Yes |
| DB activation events (which fired, when) | `agent_trace.db_activation_log` | Yes |
| CG state per step | `steps[].cg_state` | Yes |
| DB notifications per step | `steps[].db_notifications` | **No (always `[]`)** |

### How to Fix for Future Runs

Two changes should be made:

**1. Populate `db_notifications` in step traces (episode_runner.py).** After each agent step, the episode runner should copy the DB notifications from the agent into the step trace. This makes step-level traces self-contained — a reader can see DB activity alongside actions and observations without consulting a separate log.

```python
# In the step loop of episode_runner.py, after getting the agent's action:
step_trace = StepTrace(
    ...
    db_notifications=agent.get_step_notifications(),  # NEW: populate from agent
    ...
)
```

**2. Add a report template validation checklist.** The planning prompt's Section 8 (Report Template) lists 12 required sections. Future report generation should verify that all 12 sections are present before the report is finalized. The two sections omitted here (items 6 and 7) were explicitly marked as non-optional in the prompt.
