## 1. Overview

Run 11c tests two architectural changes designed to address Run 11b's identified bottlenecks:

- **Change E:** v2 Context Graph with `OBJECT_RELEVANCE_SCREENING` (5-state graph) to address the object identification bottleneck
- **Change F:** Lowered `stochasticity_hypothesis` fire_threshold from 7.0 → 6.0 to address the low stochasticity detection rate (27% in 11b)

Both changes are applied to CG-only (Cell B) and full CG+DB (Cell C). Cell A (base_llm) is unchanged.

**Key changes from Run 11b:**
- v2 CG: Adds `OBJECT_RELEVANCE_SCREENING` state between INITIAL_EXPLORATION and COMBINATION_TESTING
- `object_screening_max_steps=25` backstop for the new ORS state
- `stochasticity_hypothesis` fire_threshold lowered from 7.0 → 6.0 (Cell C only)
- `behavior_version="11c"` (Cell C only)
- Seeds 1301–1315 (vs 1201–1215 in 11b)
- Budget cap raised to $150 (vs $120)

## 8. Interpretation

### 8.1 Why Does cg_only (v2) Succeed?

The v2 CG's 3 successes (ep0, ep8, ep13) all follow the same 5-state linear traversal: IE → ORS → CT → HE → V. The agent spends:
- ~9 steps in INITIAL_EXPLORATION (individual testing)
- ~25 steps in OBJECT_RELEVANCE_SCREENING (the backstop ceiling)
- ~20-30 steps in COMBINATION_TESTING
- ~10-20 steps in HYPOTHESIS_EVALUATION
- Final steps in VERIFICATION

The ORS phase, despite always hitting the backstop, forces the agent to systematically test individual objects and pairs before moving to combinations. This structured early exploration appears to improve object identification compared to v1's direct IE → CT path.

The 3 successful episodes all correctly identified the stochastic element (`order_sensitive_stochastic`) — cg_only agents detect stochasticity through exploration patterns alone, without the explicit RELIABILITY_TESTING framework.

### 8.2 Why Does Adding DB Hurt in 11c?

In 11b, DB partially recovered from cg_only's 0% to 13%. In 11c, DB actively degrades from cg_only's 20% to 7%. The reversal occurs because:

1. **DB-added states fragment the exploration trajectory.** DB injects DIMENSION_DISCOVERY (7% visit rate), ORDER_TESTING (43% visit rate), MODERATOR_DETECTION (0% visit rate), and RELIABILITY_TESTING (78% visit rate). These additional states create branching paths that distract from the linear IE → ORS → CT → HE → V trajectory that works for cg_only.

2. **ORS backstop timing conflict.** The ORS backstop fires at step ~34 for both cells. But in Cell C, DB has already added DIMENSION_DISCOVERY (step ~7-11) and sometimes ORDER_TESTING (step ~16-25) by the time ORS completes. The agent attempts to transition to these DB-added states from ORS but **fails** because ORS can only transition to COMBINATION_TESTING. This creates 1-3 failed transition attempts per episode during ORS.

3. **Stochasticity detection without object identification = wrong answer.** Cell C detects stochasticity in 60% of episodes (7/15 with correct rule_type) but identifies correct objects in only 13% (2/15). The RELIABILITY_TESTING state drives the agent to repeat-test configurations, but if the candidate configuration includes distractors, the probability estimates are meaningless.

4. **The VER→RT self-correction loop is extremely rare.** Only 1/15 Cell C episodes exhibits the self-correction pattern that distinguishes success. The agent needs to reach VERIFICATION, realize its answer is uncertain, and return to RELIABILITY_TESTING — but the CG's forward-driving structure makes this backtracking unlikely.

### 8.3 The Object Identification Bottleneck Persists

Both Changes E and F target downstream issues (stochasticity detection, CG structure) rather than the root cause: **agents cannot reliably identify which 3 of 5 objects matter.**

The ORS state was designed to address this, but the 100% backstop fire rate reveals it's not working as intended. Agents spend 25 steps in ORS without learning to eliminate distractors. Possible reasons:
- The ORS guidelines are too open-ended ("test pairs/triples, find activations")
- With p=0.7 stochastic activation, individual object tests give noisy signal
- The transition condition from ORS → CT requires confidence the agent never develops
- 25 steps may be insufficient for reliable singleton testing with stochastic activation

## 9. Implications for Architecture Research

### 9.1 The CG-Only Sweet Spot

The most striking finding is cg_only (v2) outperforming full_cg_db (v2). This suggests a **CG complexity sweet spot**: enough structure to guide exploration (5 states), but not so much runtime modification that the agent loses coherence. The v2 CG provides the "conceptual vocabulary" for object screening without the overhead of DB's state injection and competitive inhibition.

### 9.2 DB Interference Pattern

Dynamic Behaviors appear to interfere with v2 CG in a way they didn't with v1. With v1, cg_only was at 0% — any DB contribution was positive. With v2 at 20%, DB's additions are net negative. This is consistent with a model where:
- **DB adds value when the base CG is insufficient** (v1 lacks ORDER_TESTING, RELIABILITY_TESTING)
- **DB destroys value when the base CG is already adequate** (v2's linear path is effective)

The implication: a well-designed static CG may be superior to a mediocre CG + dynamic modifications. DB should be reserved for cases where the CG genuinely cannot anticipate needed states.

### 9.3 ORS Backstop as Structural Timer

The 100% ORS backstop fire rate reveals that ORS functions as a **structural timer** (force 25 steps of individual testing) rather than a **discovery phase** (test until you can narrow candidates). A future revision could:
1. Add explicit object-elimination guidelines ("If object X never contributes to activation, mark it as a distractor")
2. Lower the ORS backstop to 15-20 steps (the agent isn't learning new information after that)
