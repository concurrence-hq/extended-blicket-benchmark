## 1. Background and Objective

### 1.1 The Blicket Detector Paradigm

The "blicket detector" is a causal learning paradigm developed by Alison Gopnik and colleagues to study how children discover causal structure. A blicket detector is a device that activates (lights up, plays music) when certain objects — called "blickets" — are placed on it. The learner's task is to figure out which objects are blickets and what causal rule governs activation.

Two standard rule types are studied:

- **Conjunctive:** ALL required objects must be on the detector simultaneously for activation (A AND B).
- **Disjunctive:** ANY single required object is sufficient for activation (A OR B).

Children consistently outperform computational models on this task — not because they're better at statistical inference within a fixed hypothesis space, but because they spontaneously consider qualitatively different kinds of hypotheses.

### 1.2 Kosoy et al. (2022): Children vs. Computational Models

Kosoy et al. (2022), "Learning Causal Overhypotheses through Exploration in Children and Computational Models" (CLeaR, PMLR 177:390-406), is the foundational paper for this experiment. Key findings:

- Children explore a "richer and larger hypothesis space" than information-gain-optimal RL models
- Children spontaneously test qualitatively different hypothesis types — not just which objects are blickets, but whether the rule itself might involve ordering, probabilistic activation, or hidden moderating variables
- This capability — **coordinate system revision** — differs fundamentally from optimizing within a fixed set of variables
- The authors concluded this "may inspire entirely new directions of research" rather than incremental improvements to existing algorithms

The gap Kosoy et al. identified is precisely what this experiment tests: can any AI architecture recover the coordinate system revision capability that children demonstrate and standard ML approaches lack?

### 1.3 Research Question

**Does compositional architecture (Context Graphs + Dynamic Behaviors) enable coordinate system revision in causal learning tasks — the capability that children demonstrate and LLM training cannot produce?**

The hypothesis: compositional architecture will show adequate performance on standard causal tasks (where bare LLMs also succeed) but superior performance on extended tasks requiring frame-shift reasoning — recognizing that the relevant causal dimensions have changed.

### 1.4 Adaptation from Kosoy et al. to Agent Testing

Kosoy et al.'s virtual blicket environment was designed for children interacting through a GUI. We adapted it for LLM agent evaluation:

**Environment.** Three objects (A, B, C) can be placed on or removed from a detector via discrete actions (`place_a`, `place_b`, `place_c`, `remove_a`, `remove_b`, `remove_c`, `check`). The detector activates according to a hidden causal rule. The agent receives text observations describing the detector state after each action. When the agent chooses `check`, it submits a guess: the rule type (conjunctive/disjunctive) and which objects are blickets.

**Agents.** Three architectures are compared, simulating progressively more compositional structure:

| Agent | Architecture | Description |
|-------|-------------|-------------|
| `base_llm` | Bare LLM | Claude Sonnet 4.5 with a task-description system prompt. No structured memory, no guided exploration strategy. Conversation history grows naturally through the episode. |
| `cg_only` | Context Graph only | Sonnet + a 4-state Context Graph injected into the system prompt each turn. States: `INITIAL_EXPLORATION` → `COMBINATION_TESTING` → `HYPOTHESIS_EVALUATION` → `VERIFICATION`. Each state provides objectives, guidelines, and transition conditions. The CG is static — it cannot be modified at runtime. |
| `full_cg_db` | Full CG + Dynamic Behaviors | Sonnet + Context Graph + 4 Dynamic Behaviors that can modify the CG at runtime. Trigger conditions are evaluated by Haiku after each step. When fired, behaviors add new states to the CG (e.g., `DIMENSION_DISCOVERY`, `ORDER_TESTING`, `RELIABILITY_TESTING`, `MODERATOR_DETECTION`), providing new objectives and guidelines for non-standard causal reasoning. |

**Scoring.** An episode is scored as correct if the agent correctly identifies both the rule type AND the set of blicket objects. Partial credit is tracked (rule_type_correct, objects_correct) but not used for the primary success metric.

## 2. Experimental Conditions

### 2.1 Phase 3: Standard Conditions

Standard conditions test whether agents can solve the basic blicket task — the same task types used in Gopnik's developmental studies.

#### Conjunctive

- **Rule:** Objects A AND B must both be on the detector for activation. C is a non-blicket.
- **Key challenge:** The agent must discover that neither A nor B alone activates the detector, but A+B together does. C never activates.
- **Difficulty:** Moderate — requires testing combinations, not just individual objects.

#### Disjunctive

- **Rule:** Either A OR B alone is sufficient for activation. C is a non-blicket.
- **Key challenge:** The agent must discover that A alone activates, B alone activates, but C does not. The rule is easier to discover because individual object tests are informative.
- **Difficulty:** Lower — individual testing reveals the answer.

**Design:** 2 conditions x 3 agents x 30 episodes = **180 episodes**

### 2.2 Phase 4: Extended Conditions

Extended conditions test whether agents can reason about non-standard causal structures — the kinds of hypotheses that children spontaneously consider but computational models typically miss (Kosoy et al., 2022).

#### Order-Sensitive

- **Underlying rule:** Conjunctive (A AND B required).
- **Extension:** Objects must be placed in the specific order A-then-B. The environment tracks a global placement history. The order check filters this history to required objects and verifies the subsequence matches `["A", "B"]`.
- **Key challenge:** The agent must discover that the same set of objects {A, B} produces different results depending on placement order.
- **Difficulty:** High — requires shifting from "which objects" to "in what sequence."
- **Implementation detail:** The `_placement_order` list is append-only and accumulates across the entire episode. Every `place_X` action appends to this list regardless of prior removals. The order check (`_check_order`) filters this global history to just the required objects and checks if the filtered subsequence exactly equals the required order. This means that once an agent places both A and B in any context (e.g., testing them individually), subsequent placements of A or B add additional entries to the history, potentially making the filtered subsequence longer than the required order and causing the check to fail permanently.

#### Stochastic

- **Underlying rule:** Conjunctive (A AND B required).
- **Extension:** When the rule IS satisfied, the detector activates with probability 0.7 (not 1.0). When the rule is NOT satisfied, the detector never activates.
- **Key challenge:** The agent must infer the rule despite inconsistent evidence — the same correct configuration sometimes activates and sometimes doesn't.
- **Difficulty:** High — requires statistical reasoning about probabilistic causation.
- **Seeds:** Each episode uses a deterministic seed for reproducibility.

#### Hidden Moderator

- **Initial rule:** Conjunctive — A AND B required.
- **Extension:** After 3 successful activations, the rule silently switches to a different rule: Disjunctive with only C as the blicket. The agent is never told the rule has changed.
- **Key challenge:** The agent must detect that a previously working rule has stopped working, abandon its established hypothesis, and re-explore to discover the new rule.
- **Difficulty:** Highest in terms of cognitive flexibility — requires recognizing that the "coordinate system" itself has changed.
- **Note:** The environment's `check_answer` evaluates against the current (post-switch) rule, so agents must identify the *new* rule to succeed.

**Design:** 3 conditions x 3 agents x 30 episodes = **270 episodes**

## 4. Trace Analysis: Order-Sensitive Failures

The most striking result is the 0% success rate for both compositional agents on order_sensitive, compared to 93.3% for the bare LLM. Trace analysis reveals the root cause is an interaction between the Context Graph's exploration strategy and the environment's order-tracking implementation.

### 4.1 How the Order Check Works

The `ExtendedBlicketEnv` maintains a global `_placement_order` list. Every `place_X` action appends the object name, regardless of what was previously placed or removed. The `_check_order` method filters this list to just the required objects (A and B) and checks whether the filtered subsequence exactly equals `["A", "B"]`.

```python
def _check_order(self) -> bool:
    required = self.order_config.required_order  # ["A", "B"]
    placed_required = [o for o in self._placement_order if o in required]
    return placed_required == required
```

This means: if A is placed, then removed, then B is placed, then removed, then A is placed again and B is placed — the placement history is `["A", "B", "A", "B"]`. The filtered subsequence is `["A", "B", "A", "B"]`, which does NOT equal `["A", "B"]`. **The order is permanently corrupted.**

### 4.2 The Base LLM's Accidental Success

The bare LLM has no structural guidance telling it to test objects individually first. Its natural exploration pattern is:

```
Step 0: place_a → INACTIVE (A alone)
Step 1: place_b → ACTIVE!  (A+B, placement_order = ["A", "B"] ✓)
```

The LLM leaves A on the detector while adding B. This "lazy" approach accidentally creates the only valid placement sequence — A placed first, then B, with no duplicate entries. The detector activates on the very first A+B test.

The LLM then spends the remaining ~26 steps trying unsuccessfully to reproduce the activation (because all subsequent placements corrupt the history), but ultimately trusts its single positive observation from step 1 and submits the correct answer.

**Example (base_llm ep000):**
```
Step  0: place_a  → det=['A']     active=False
Step  1: place_b  → det=['A','B'] active=True  ← ACTIVATION!
Step  2: remove_a → det=['B']     active=False
...steps 3-26: various tests, no further activations...
Step 27: check    → submits conjunctive, {A, B} → CORRECT
```

Placement order history: `['A', 'B', 'C', 'A', 'A', 'C', 'A', 'B', 'A', 'B', 'C', 'B', 'B', 'A', 'C']`

The activation at step 1 occurred because the filtered subsequence at that point was exactly `["A", "B"]`. All subsequent tests failed because the filtered subsequence grew beyond `["A", "B"]`.

### 4.3 The CG Agent's Systematic Failure

The Context Graph's `INITIAL_EXPLORATION` state has a guideline: **"Clear the detector between tests for clean observations."** This causes the agent to test objects individually with removal between each test:

```
Step  0: place_a  → det=['A']  active=False  [CG: INITIAL_EXPLORATION]
Step  1: remove_a → det=[]     active=False  [CG: INITIAL_EXPLORATION]
Step  2: place_b  → det=['B']  active=False  [CG: INITIAL_EXPLORATION]
Step  3: remove_b → det=[]     active=False  [CG: INITIAL_EXPLORATION]
Step  4: place_c  → det=['C']  active=False  [CG: INITIAL_EXPLORATION]
Step  5: remove_c → det=[]     active=False  → transitions to COMBINATION_TESTING
```

After individual testing, `_placement_order` = `["A", "B", "C"]`. The filtered subsequence is already `["A", "B"]` — which is correct! But the CG agent has already removed everything.

When it then tests A+B together in `COMBINATION_TESTING`:

```
Step  6: place_a  → det=['A']     active=False  [CG: COMBINATION_TESTING]
Step  7: place_b  → det=['A','B'] active=False  [CG: COMBINATION_TESTING]
```

Now `_placement_order` = `["A", "B", "C", "A", "B"]`. Filtered: `["A", "B", "A", "B"]` ≠ `["A", "B"]`. **The order was permanently poisoned by the second placement of A and B.** The detector never activates.

The agent exhaustively tests all combinations (AB, AC, BC, ABC), sees zero activations for any configuration, concludes "no objects are blickets," and either fails to submit an answer (the parser doesn't accept "none") or submits an incorrect answer.

**Example (cg_only ep000):**
```
Step  0: place_a  → active=False  [INITIAL_EXPLORATION]
Step  1: remove_a → active=False  [INITIAL_EXPLORATION]
Step  2: place_b  → active=False  [INITIAL_EXPLORATION]
Step  3: remove_b → active=False  [INITIAL_EXPLORATION]
Step  4: place_c  → active=False  [INITIAL_EXPLORATION]
Step  5: remove_c → active=False  [COMBINATION_TESTING]
Step  6: place_a  → active=False  [COMBINATION_TESTING]
Step  7: place_b  → active=False  [COMBINATION_TESTING]  ← NO activation!
...all combinations fail...
Step 18: check    → answer="none" → PARSE FAILURE
```

Placement order history: `['A', 'B', 'C', 'A', 'B', 'A', 'C', 'B', 'A']`
Filtered for required objects: `['A', 'B', 'A', 'B', 'A', 'B', 'A']` ≠ `['A', 'B']`

### 4.4 The Full CG+DB Agent's Identical Failure

The `full_cg_db` agent uses the same Context Graph and follows the same systematic exploration strategy. The Dynamic Behaviors — designed to fire when observations contradict standard hypotheses — never activate because the agent never observes a positive activation to then see contradicted. Without any activation events, there is no prediction error, and the DB triggers (which require `had_unexpected_result=True` or at least 8-10 steps of evidence) never fire.

**Example (full_cg_db ep000):**
```
Step  0: place_a  → active=False  [INITIAL_EXPLORATION]
Step  1: remove_a → active=False  [INITIAL_EXPLORATION]
Step  2: place_b  → active=False  [INITIAL_EXPLORATION]
Step  3: remove_b → active=False  [INITIAL_EXPLORATION]
Step  4: place_c  → active=False  [INITIAL_EXPLORATION]
Step  5: place_a  → active=False  [COMBINATION_TESTING]
Step  6: place_b  → active=False  [COMBINATION_TESTING]  ← NO activation!
...all combinations fail...
Step 10: check    → answer="none" → PARSE FAILURE
```

Placement order history: `['A', 'B', 'C', 'A', 'B', 'C']`
DB activations: none (no trigger conditions met)

### 4.5 Two Distinct Issues

**Issue 1: Environment implementation is fragile.** The `_check_order` method uses a global, append-only placement history with an exact-match check. This means any agent that tests required objects individually before testing them in combination will permanently corrupt the order and never observe activation. Only an agent that places A-then-B as its very first two actions can succeed. This punishes systematic exploration and rewards accidental exploration patterns.

**Issue 2: The CG cannot represent temporal hypotheses.** The 4-state Context Graph models the task as a static set-membership problem. Its states (`INITIAL_EXPLORATION`, `COMBINATION_TESTING`, `HYPOTHESIS_EVALUATION`, `VERIFICATION`) encode a strategy for discovering *which objects* matter, but provide no guidance for considering *in what order* they must be placed. The CG guidelines explicitly instruct "clear the detector between tests" — a reasonable strategy for set-membership inference that is fatal for order-sensitive rules.

**Issue 3: DB triggers require positive evidence to fire.** The Dynamic Behaviors are designed to fire when observations contradict expectations (e.g., the same configuration sometimes works and sometimes doesn't). But in the order_sensitive condition, the CG agents never observe ANY activation, so there's no contradiction to detect — just uniform non-activation, which the agent interprets as "no objects are blickets."

### 4.6 The 2 Base LLM Failures

The base LLM failed on 2 of 30 order_sensitive episodes (episodes 2 and 20). In both cases, `answer_submitted` was false — the agent failed to submit a parseable answer, not that it submitted a wrong answer. These likely represent cases where the LLM's first actions happened to place B before A (or placed them individually before combining), poisoning the order early, resulting in zero observed activations and a "none" answer that couldn't be parsed.

## 5. Stochastic and Hidden Moderator Results

### 5.1 Stochastic Condition

The stochastic condition (p=0.7 activation when rule satisfied) produced differentiation between agents, with `base_llm` and `full_cg_db` both at 80% and `cg_only` at 60%.

The dominant failure mode was **incorrect object identification** — agents could often identify the rule type (conjunctive) but selected the wrong blicket set. This is expected: stochastic feedback makes it harder to distinguish "this object is irrelevant" from "this object is relevant but the detector randomly didn't activate."

Notable: `full_cg_db` matched `base_llm` accuracy (80%) but used 2.6x more steps (30.5 vs 11.7) and 6.3x more cost ($0.562 vs $0.089). The Dynamic Behavior engine adds overhead without accuracy benefit on this task.

### 5.2 Hidden Moderator Condition

All agents performed reasonably well on hidden_moderator (83-90%), with `base_llm` leading at 90%. This condition — where the rule silently switches after 3 successful activations — was expected to be the hardest for agents without architectural support for detecting rule changes.

The relatively high accuracy across all agents suggests that LLMs handle sudden environmental shifts better than expected. The rule switch (from conjunctive A+B to disjunctive C-only) produces a dramatic enough behavioral change (previously working configurations stop working) that even the bare LLM notices and re-explores.

## 7. Summary and Open Questions

### 7.1 Key Findings

1. **Standard conditions don't differentiate agents.** All three architectures achieve 100% accuracy on conjunctive and disjunctive tasks. The bare LLM does it faster and cheaper.

2. **Extended conditions break the ceiling.** Overall accuracy drops to 63.7%, with large differences between agents.

3. **The bare LLM outperformed compositional architectures on every extended condition.** This is the opposite of the hypothesized direction. The base_llm degraded 12pp from standard to extended; the compositional agents degraded 44-52pp.

4. **Order-sensitive is catastrophic for compositional agents (0% vs 93%).** Root cause: the CG's "clean between tests" guideline interacts fatally with the environment's append-only order tracking. The bare LLM succeeds accidentally through "lazy" exploration.

5. **Stochastic shows partial differentiation.** `full_cg_db` matches `base_llm` at 80%, while `cg_only` lags at 60% — suggesting the DB component helps with probabilistic reasoning, though at much higher cost.

6. **Hidden moderator is surprisingly easy for all agents (83-90%).** The rule switch produces such a dramatic behavioral change that even bare LLMs detect and adapt.

### 7.2 Open Questions

1. **Is the order_sensitive result a fair test?** The environment's append-only placement history means that any systematic exploration strategy will fail. Should `_check_order` be redesigned to track order relative to the current detector state (resetting on removal)?

2. **Why doesn't the CG help on hidden_moderator?** This is the condition most aligned with coordinate system revision, yet the bare LLM outperforms both compositional agents. Is the LLM's implicit flexibility (through attention over its full conversation history) more effective than explicit architectural scaffolding?

3. **Are the Dynamic Behaviors firing at the right times?** On order_sensitive, they never fire because there's no positive evidence to contradict. On stochastic and hidden_moderator, are they contributing to the `full_cg_db` agent's performance, or is the CG-only component doing the work?

4. **What exploration strategies do the agents use?** The traces contain full conversation histories — systematic analysis of exploration patterns (hypothesis types considered, test strategies, reaction to unexpected results) would reveal whether the compositional agents show qualitatively different reasoning, even when their accuracy doesn't reflect it.

5. **How should the CG be redesigned?** The current CG models the task as static set-membership inference. Adding order-aware guidelines, probabilistic reasoning guidance, and rule-change detection instructions could address the specific failure modes identified here.

6. **Is there an environment design that fairly tests coordinate system revision?** The order_sensitive condition's fragility suggests the environment implementation needs revision. What implementation of temporal ordering would allow systematic exploration while still testing whether agents can discover that order matters?
