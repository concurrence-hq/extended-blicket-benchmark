## 8. Interpretation

### 8.1 Why Does CG-Only Fail So Badly?

The static 4-state CG (INITIAL_EXPLORATION → COMBINATION_TESTING → HYPOTHESIS_EVALUATION → VERIFICATION) lacks the conceptual vocabulary for order-sensitive or stochastic reasoning. Without ORDER_TESTING and RELIABILITY_TESTING states — which only Dynamic Behaviors can create — the agent:

1. **Cannot frame the order hypothesis** — the CG never suggests testing permutations
2. **Cannot frame the stochasticity hypothesis** — the CG never suggests repeat-testing for probability estimation
3. **Over-explores in COMBINATION_TESTING** — spends ~47 steps before reaching HYPOTHESIS_EVALUATION, testing combinations without a systematic strategy
4. **Submits wrong answers confidently** — 10/15 submitted answers (67% submission rate) but 0% correct

The cg_only condition is functionally a base_llm with a rigid exploration structure imposed on it. The structure constrains without guiding, producing worse-than-unscaffolded performance.

### 8.2 Why Doesn't DB Fully Recover?

DB successfully adds ORDER_TESTING (100% reach rate, step ~21) and RELIABILITY_TESTING (27% reach, step ~40). But recovery is incomplete because:

1. **Stochasticity detection is rare** — with 3 objects, the agent must place all 3 in correct order to trigger activation; inconsistent results from identical configurations are much less frequent than with 2 objects
2. **Late stochasticity detection** — when it fires (step ~40), less than 60% of the step budget remains for repeat-testing
3. **Object identification is the bottleneck** — 47% of failures are `wrong_objects`, meaning the agent hasn't identified which 3 of 5 objects are correct before attempting order/stochasticity analysis
4. **CG overhead persists** — the system prompt with CG context consumes tokens without providing proportional guidance benefit at the object-identification stage

### 8.3 Why Does Base LLM Win?

The base_llm agent succeeds through:

1. **Unconstrained exploration** — free to follow any hypothesis without CG state obligations
2. **Implicit pattern matching** — Sonnet 4.5's training data includes enough causal reasoning to sometimes detect stochastic patterns without explicit scaffolding
3. **No structural overhead** — shorter prompts, more efficient token usage
4. **Lucky on easy rules** — both of its unique successes (ep011, ep014) have rules with simpler structures

### 8.4 Decision Tree Resolution

Per the pre-registered decision tree from the Run 11b prompt:

- **If base_llm > full_cg_db:** Investigate scaffold cost mechanisms → **CONFIRMED** (27% > 13%)
- **If cg_only = 0%:** CG is actively harmful without DB → **CONFIRMED**
- **If full_cg_db > cg_only but < base_llm:** DB provides partial recovery but CG overhead dominates → **CONFIRMED** (13% > 0% but < 27%)

**Verdict:** The scaffold *cost* emerging in Run 11a (−7pp) is amplified in 11b (−13pp). Critically, the scaffold showed *benefit* on deterministic ORDER_SENSITIVE (10e: +10pp, 10f: +20pp) — the reversal to negative Δ occurs specifically when stochasticity is introduced. On 3-object ORDER_STOCHASTIC, the CG imposes coordination costs that exceed the benefits of structured exploration. DB partially mitigates but cannot fully overcome.

## 9. Implications for Compositional Architecture Research

### 9.1 Task Difficulty Threshold

There appears to be a **difficulty threshold** beyond which scaffold costs exceed benefits. The transition occurs between:
- 2-object ORDER_STOCHASTIC (11a): scaffold cost = −7pp, both cells perform well (67-73%)
- 3-object ORDER_STOCHASTIC (11b): scaffold cost = −13pp, all cells perform poorly (0-27%)

This suggests the current CG/DB architecture is beneficial when the base model can already solve the task at moderate rates, and harmful when the task is too hard for the base model.

### 9.2 The Object Identification Bottleneck

The dominant failure mode (wrong_objects: 47%) reveals that the current CG is optimized for the wrong phase. The 4-state graph spends its structure budget on hypothesis evaluation and verification, but the actual bottleneck is earlier: identifying which 3 of 5 objects matter. A CG designed for 3-object tasks might need states like OBJECT_SCREENING or SINGLETON_TESTING to systematically narrow the candidate set before attempting combination/order analysis.

### 9.3 Stochasticity Detection Scaling

stochasticity_hypothesis fired in only 27% of episodes (vs ~67% expected based on Run 11a). With 3 objects, the trigger condition ("same configuration, different results") is inherently harder to satisfy because:
- The agent must correctly assemble all 3 objects in order (rare in early exploration)
- The stochastic element (p=0.7) means some correct configurations won't activate
- With 2 distractors, there are many more "noise" observations to parse

A future revision might lower the fire_threshold or add an explicit object-narrowing phase before stochasticity evaluation.
